# グループ議論 P5「議論中の調査」計画書 (JAR-104)

状態: **計画(案)。未承認、未実装。** 実装はメンテナーが §8 に答えてから、別の Issue と PR で行う。親計画: [group-discussion-plan.md](group-discussion-plan.md) §5 の P5。仕組み: [discussion.md](discussion.md)、[research.md](research.md)。検索プロバイダーは Tavily に決定済み(2026-10-16、既定オフ)。

## 1. 目的

議論の参加者が、根拠のない数字や主張を言い合うのを減らす。計画書 §7 の「幻覚」への対策として、議論の前、または議論の途中に、既存の Research Engine で出典付きの事実を集め、議論の材料にする。

含まない: 参加者による自由な web 閲覧、ツール(ファイル・シェル)の使用、調査結果の自動承認、議論中の記憶の書き込み。

## 2. 既に使えるもの

| 必要なもの | 既にあるもの |
|---|---|
| 調査の実行 | `ResearchRunService.submit(question, level)`(一度に 1 件、ローカルの検索予算、質問の規則を含む)。チャットの `ResearchStarter` が同じ入口を使っている |
| 検証済みの主張と出典 | `backend/chat/research_answer.py` の `Evidence`(主張、出典、矛盾)。出典のない主張は答えに出さない既存の規則 |
| 進捗と中止 | タスクキューと `/api/tasks`。議論も調査も同じタスク画面に出る |
| 議論側の入口 | `DiscussionEngine` の `emit`、`is_cancelled`、停止コード、`【お知らせ】` 形式 |

新しい検索経路や読み取り経路は作らない。調査は必ずこの 1 本を通す。

## 3. 案: 議論の前に 1 回だけ調査する(推奨)

```
議論の開始 ─► (オプション)調査 1 回 ─► 検証済みの主張を「資料」として全員に渡す ─► 通常の議論 ─► まとめ
```

- 利用者が議論の開始時に「調査してから議論」を選んだときだけ動く。既定は今までどおり調査なし。
- 調査の問いは、議論のお題そのまま(利用者が書いた文)。ペルソナの設定や過去の発言は検索に送らない。
- 水準は Quick 固定(検索の消費が最小)。Standard 以上は第 2 版で検討する。
- 調査が終わるまで議論は始まらない。待ち時間の上限を置き、超えたら調査なしで議論を始めて `【お知らせ】`(固定コード)で伝える。
- 資料は、検証済みの主張と出典(タイトルと URL)だけ。ページ本文、ベンダーの生成回答、検索の生の結果は渡さない。長さに上限を置く。
- 各参加者のプロンプトには「資料にある事実は出典を挙げてよい。資料にない数字は `要確認`」と書く。まとめは、資料の出典を `要確認の数字` とは別に載せる。
- 資料は議論の会話に、`【資料】` 形式の 1 件のメッセージとして残す(出典 URL つき)。後から読み返せる。

### 採用しない案

| 案 | 理由 |
|---|---|
| 発言者が必要に応じて何度でも調査を呼ぶ | 費用と時間が読めない。1 議論あたりの検索数に上限が付けにくい。第 2 版以降 |
| ラウンドごとに調査する | 同上。Tavily 無料枠(月 1,000)を議論 1 回で使い切るおそれ |
| まとめの後に事実確認だけ調査する | 議論の質には効かない。「要確認の数字」の検証は別の機能として検討できる |

## 4. 費用と上限

- 調査 1 回あたり、Quick が使う検索数だけ(現行の Quick の上限に従う)。ローカルの月次検索予算(`JARVIS_SEARCH_MONTHLY_LIMIT`)の対象に入る。予算がなければ調査なしで議論を続ける。
- 議論 1 回あたり調査は最大 1 回。1 日あたりの議論数(`JARVIS_DISCUSSION_PER_DAY_LIMIT`)の中で数える。
- 調査用の設定は 1 つだけ増やす案: `JARVIS_DISCUSSION_RESEARCH`(既定オフ。`JARVIS_DISCUSSION`、`JARVIS_RESEARCH_ENABLED`、検索プロバイダーが揃っていることが条件)。`doctor` に行を足す。

## 5. 失敗時の動き

| 状況 | 動き |
|---|---|
| 調査が無効、検索予算なし、検索プロバイダーなし | 調査なしで議論。お知らせは出さない(利用者が選べない状態にする) |
| 調査の失敗・タイムアウト・検証済みの主張なし | 調査なしで議論を始め、`RESEARCH_SKIPPED` のお知らせを出す。偽の資料は作らない |
| 利用者が中止 | 調査も議論も止める。調査の途中結果は渡さない |
| 資料に指示のような文が含まれる | 資料は常に「参考情報」として囲んで渡し、参加者の指示にはしない(出典の文は信用しない既存の方針) |

## 6. プライバシー

お題の文が検索サービス(Tavily)に送られる。利用者が「調査してから議論」を選んだときだけ送られることを、画面の選択肢の近くに書く。ペルソナの内容、過去の議論、記憶は送らない。ログにはお題・資料・出典の本文を出さず、固定のイベント名とコードだけにする。

## 7. 実装の分け方(承認後)

1. エンジンと資料の形式(偽の調査器で単体テスト): 資料の注入、上限、失敗時の動き。
2. サービスとタスク: 調査を呼ぶ、待つ、中止する。設定とドクター。
3. 画面: 「調査してから議論」の選択と資料の表示。
4. 実環境の確認: Tavily と Gemini で 1 回通す(メンテナーの手元の鍵、少数回)。

PR は少なくまとめる方針なので、1〜3 を 1 本にまとめる案を推奨する。

## 8. メンテナーに決めてほしいこと(推奨つき)

1. 調査のタイミング: 議論の前に 1 回だけ(推奨)か、途中でも許すか。
2. 水準: Quick 固定(推奨)か、選べるようにするか。
3. 既定: 調査は選んだときだけ(推奨)か、お題の内容で自動判断するか。
4. 資料を議論の会話に残すか(推奨: 残す)。
5. 待ち時間の上限(推奨: 既存のチャット調査の既定 180 秒より短い 90 秒)。
6. まとめの `要確認の数字` を調査で検証する機能を、別 Issue にするか。
