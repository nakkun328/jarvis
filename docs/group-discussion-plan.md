# グループ議論(複数 AI の討論)計画書

状態: 計画(メンテナーが承認済み。§8 の決定は、すべて推奨のとおり)。実装はこれから(P1 から)。

## 1. 目的

質問や相談を、役割の違う 3 体前後の AI に議論させ、1 つの会話(グループチャット)として読めるようにする。
一人の AI の答えより、見落としを減らし、反対意見や別の見方を得ることが目的。

- 各 AI(ペルソナ)に、名前、役割、立場、**指摘してほしい点**、口調、使うモデルを設定する。
- 3 体が順番に発言し、互いに反論・補足する。最後に、まとめ役が結論と未解決の点を出す。
- 実際のグループチャットのように、発言者ごとに、名前と色が付いた吹き出しで見える。

### 例

| ペルソナ | 役割 | 指摘してほしい点 | モデルの例 |
|---|---|---|---|
| 設計者 | 案を出す | 全体の筋、代案 | openai |
| 批判役 | 穴を探す | 前提の誤り、数字の根拠、見落とし | gemini |
| 現実担当 | 実行可能性 | 費用、時間、手間、安全 | groq |
| まとめ役(Jarvis) | 司会・要約 | 合意点・対立点・次の一歩 | 既定のモデル |

## 2. 範囲

含む: 議論の設定、実行、表示、停止、要約、履歴の保存。
含まない(最初の版): 音声、ツール(ファイル・シェル)の使用、ペルソナによる記憶の書き込み、議論中の web 調査(第 2 版で検討)。

## 3. 既存の仕組みの再利用

| 必要なもの | 既にあるもの |
|---|---|
| ペルソナごとのモデル選択 | `backend/providers/choices.py`(許可リスト `JARVIS_MODEL_CHOICES` の `provider:model`) |
| 長い処理を会話から切り離す | Task キューと、会話へ後から投稿する仕組み(チャットのツールで実装済み: `backend/chat/tool_jobs.py`) |
| 会話の保存と、後からの再開 | 会話の永続化と履歴一覧(`backend/api/chat_history.py`) |
| 進捗の表示 | Activity イベントとタスク画面 |
| 安全なエラー表示 | 固定のエラーコード方針(本文を載せない) |

新しく作るのは、(a) ペルソナ定義、(b) 議論の進行役(オーケストレーター)、(c) 表示の画面。

## 4. 設計

### 4.1 ペルソナ定義

```
name            表示名(1〜20 文字)
role            役割の一文(例: 「前提を疑う批判役」)
stance          立場・口調の指示(最大 500 文字)
checklist       必ず指摘する点のリスト(最大 5 項目、各 100 文字)
model           許可リストの `provider:model` のみ
color           表示色(固定パレットから選ぶ)
```

- モデルは、サーバー側の許可リストにある値だけ。自由入力は拒否する(既存の `model-select` と同じ)。
- 定義の本文は、AI への指示になる。ユーザー本人の入力として扱い、ログには載せない。

### 4.2 議論の進行(オーケストレーター)

1. 入力: 議題、参加ペルソナ(2〜4 体)、ラウンド数(1〜3、既定 2)。
2. 各ラウンドで、全員が 1 回ずつ発言する。発言の順番は固定の巡回(ランダムにしない)。
3. 各発言の入力は「議題 + これまでの全発言 + 自分の役割と指摘してほしい点」。他のペルソナの設定は見せない。
4. 最後に、まとめ役が、合意点・対立点・未解決・次の一歩を、短く書く。
5. 停止条件: 規定のラウンドの完了、ユーザーによる停止、呼び出し数・文字数の上限、プロバイダーの失敗(3 回続けて)。
6. 同じ意見の繰り返しを減らすため、各発言に「前の発言と同じことを繰り返さず、新しい点だけを言う」と指示する。同意だけの発言は短く切る。

### 4.3 実行と表示

- 議論は、**裏のタスク**として動かす(チャットのツールと同じ方式)。画面を止めない。
- 発言は、できた順に会話へ投稿し、画面は一定間隔で取得して追加する(既存の取得 API の `after` を利用)。
- 新しい画面 `/discussion`(または、チャット画面の「議論」モード)。入力欄、参加者の選択、ラウンド数、開始、停止。
- 発言は、名前と色つきの吹き出し。まとめは、枠で目立たせる。DOM はテキストノードのみ(`innerHTML` を使わない)。
- 議論は 1 つの会話として保存され、履歴一覧から再開・閲覧できる。

### 4.4 保存

- 発言者の名前は、メッセージに必要。現在のメッセージ表は、発言者名の列を持たない。
  - 案 A(推奨): DB を拡張する(次のスキーマバージョン。**加算のみ**。メンテナーの許可が必要)。
  - 案 B(暫定): 本文の先頭に、固定の形式 `【名前】` を付ける。DB の変更は不要。後から A に移せる。
- ペルソナ定義の保存場所:
  - 案 A(推奨): DB の新しい表(同じく、メンテナーの許可が必要)。
  - 案 B(暫定): 環境変数で指す JSON ファイル。画面からの編集は、第 2 版に回す。

### 4.5 記憶との関係

- 議論の発言は**意見**であり、事実の裏付けではない。既定では、議論の発言を、自動で記憶にしない。
- ユーザーが「まとめ」を、記憶の候補にするボタンを押したときだけ、既存の候補の仕組み(承認待ち)に入れる。
- オーナー判断(後日): 議論のまとめを自動で記憶にする、既定オフの例外を追加した(`JARVIS_DISCUSSION_MEMORY_AUTO` など、[memory.md](memory.md))。「AIの意見・事実の裏付けなし」と明示し、承認待ちが既定。
- 議論の参加者に、記憶の中身を渡すかは、決めてほしい点(§8)。

### 4.6 安全と費用

- 呼び出し数の上限: 1 議論あたり、(参加者数 × ラウンド数 + 1)回。最大でも 4 × 3 + 1 = 13 回。
- 1 日あたりの議論の回数の上限(既定 10)。上限は設定にする。
- 1 発言の最大文字数(既定 600 字)。入力に載せる過去発言の合計にも上限を置く(古い発言は、要約に置き換える)。
- 3 体のうち 1 体のプロバイダーが失敗しても、残りで続ける。3 回続けて失敗したら、議論を止める。
- web の文章など、信頼できないテキストは、議題に混ぜない(第 1 版は調査なし)。
- API キーは、既存どおり、環境変数のみ。ペルソナ定義にも、ログにも、キーは入らない。
- 既定は**無効**。有効にする設定(例 `JARVIS_DISCUSSION=1`)と、`python -m backend.doctor` の行を足す。

## 6. 受け入れ条件

- 3 体の AI(別々のモデル)が、設定した役割と指摘点に沿って、順番に発言する。
- 最後に、まとめが 1 回出る。
- 停止を押すと、次の発言が始まらずに止まる。
- 上限を超える議論は、始まらない、または途中で止まり、理由が画面に出る。
- 議論は、履歴から読み返せる。
- 鍵や設定の本文が、ログ・エラー・画面に出ない。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| AI 同士が同意し合うだけになる | 批判役に「反対の根拠を必ず 1 つ挙げる」指摘点を持たせる。繰り返しを禁じる指示 |
| 費用が増える | 呼び出し数・日次の上限。既定は無効。軽いモデルを既定にする |
| 遅い(順番に呼ぶ) | 裏のタスク。発言ができ次第、表示する |
| モデルごとの癖(Groq の制限など) | モデルの失敗は、固定のエラーコードで扱い、残りで続ける |
| 長い議論で、入力が肥大化する | 過去発言の合計に上限。古い発言を要約に置き換える |
| 幻覚(根拠のない断定) | まとめに「根拠がない主張」を、別枠で出す。第 2 版で、調査と連携する |

## 8. メンテナーの決定(2026-10-13、すべて推奨のとおり)

1. **DB の拡張を許可するか**(§4.4 の案 A)。推奨: 許可する。許可がなければ、暫定の案 B で始める。
2. **画面の置き場所**: 新しい画面 `/discussion`(推奨)か、チャット画面のモード切り替えか。
3. **議論の参加者に、記憶の内容を渡すか。** 推奨: 第 1 版では渡さない(意見が記憶に混ざるのを避ける)。
4. **まとめ役を、誰にするか。** 推奨: 既定のモデル(Jarvis の人格)。
5. **日次の上限の既定値**(推奨: 10 回/日)と、ラウンド数の最大(推奨: 3)。
6. 最初に入れるプリセットの 3 体(上の例でよいか)。
