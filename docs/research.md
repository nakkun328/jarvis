# Research design

The research engine is planned for Phase 3. It will select a level from memory only, quick search, standard research, deep research, or extensive research. A user-specified level takes priority.

The workflow is query planning, search, source collection, evaluation, reading, cross checking, conflict detection, additional search when needed, synthesis, citations, and reusable research memory. Sources may include web search, official documentation, academic sources, forums, user files, prior research, and connected personal services as those connectors become available.

Source records should include title, publisher or source, URL, publication date when known, and retrieval date. Claims should retain links to their supporting sources. Evaluation considers authority, freshness, primary versus secondary status, relevance, and agreement. When reliable sources disagree, the response should describe the disagreement and the limits of verification.

Stored findings require freshness checks before reuse; the interval depends on how quickly the subject changes.

## Data model (R1)

Research state is stored in SQLite (the tables arrived in schema version 6 and v8 extended them, both applied by the existing migration path; older data is kept and a database from a newer schema is refused). The code lives in `backend/research/models.py` (frozen dataclasses and enums) and `backend/research/repository.py` (`ResearchRepository`).

- `research_sessions`: question, level (`memory`, `quick`, `standard`, `deep`, `extensive`; default `quick`), status, result text, and a failure reason. Timestamps are UTC ISO strings and IDs are UUID text.
- `research_queries`: the search queries of a session, in order (`id`, `session_id`, `text`, `position`, `created_at`).
- `research_sources`: URL, final URL, title, publisher, publication date, retrieval time, SHA-256 digest of the content read, source type, and five independent nullable ratings (authority, freshness, primary, relevance, agreement; each 0 to 1). The same final URL with the same digest is stored once per session; a repeat returns the existing row. Page text is not stored.
- `research_claims`: a claim, the supporting source, a quote of at most 500 characters, and optional quote offsets. The database requires the source to belong to the same session, so a citation cannot point across sessions.

Status transitions are compare-and-swap with an allowed-transition table: `pending` to `running` or `cancelled`; `running` to `waiting`, `completed`, `failed`, or `cancelled`; `waiting` to `running`, `cancelled`, or `failed`. `failed`, `completed`, and `cancelled` are final: the session, its queries, sources, and claims no longer change. Completion happens only through `set_result` on a running session, which stores the bounded result text. A failure stores one of a fixed set of short codes (`search_failed`, `no_results`, `reader_failed`, `synthesis_failed`, `timeout`, `budget_exceeded`, `internal_error`), never an upstream message.

The repository offers no physical deletion. The Quick Research pipeline that fills these tables is described in [research-quick.md](research-quick.md).

Standard Research (several passes, cross-check, conflicts, bounded follow-up searches) and the follow-up query generator are described in [research-standard.md](research-standard.md).

Level selection, the deterministic query planner, source type classification and the authority, freshness and relevance ratings (R2, not yet wired into Quick Research) are described in [research-quality.md](research-quality.md).

## Source evaluation, cross-check, conflicts and the search decision (schema v8)

Schema v8 is additive (nullable columns, new tables; a v7 database upgrades in place, old rows stay valid, and re-running the migration changes nothing). All of it is library code: nothing here searches, fetches a page, calls a model or creates a research session by itself; the pipelines run only when a research is requested (see [Requesting a research](#requesting-a-research-off-by-default)).

- **Persisted classification and reasons (JAR-42/43/45).** `research_sources` gains `classification_rule` and `classification_basis` (how the source type was decided: a rule id such as `docs_host` and `host`/`path`/`title`/`default`/`provided`). The new table `research_source_reasons` keeps, per rating (`authority`, `freshness`, `relevance`, `agreement`), up to four fixed reason codes (`RatingReason`, validated per rating on every write; the database only accepts lower-case identifier-shaped codes). `ResearchRepository.set_source_classification`, `set_evaluation(..., reasons=...)` and the atomic `set_source_assessment` write them, only while the session is open; `evaluate_and_store` now stores the type, rule, basis and the three reasons together and does not reclassify a source that already has a recorded rule. A source stored before v8 simply has no rule or reasons (`null` and empty lists in the API).
- **Cross-check (JAR-46, `crosscheck.py`, `facts.py`).** For each stored claim, the text the caller read from each source (page text is not stored) is searched for the sentence on the same subject, and the source gets a stance: `supports` (verbatim quote, or matching numbers/dates/entities), `partial`, `contradicts` (different figure with the same unit, different date, or opposite negation) or `silent`. The `agreement` rating of a source is the mean share of the other speaking sources that took the same side; with no other source speaking it is `null` with `agreement_no_comparison`. Sources of the same registrable domain are not "other" sources for each other (one site is not independent confirmation), and in a claim's rating the pages of one domain count as one speaker. Reasons: `agreement_corroborated`, `agreement_mixed`, `agreement_contradicted`, `agreement_no_comparison`, `agreement_verbatim_support`, `agreement_number_mismatch`, `agreement_date_mismatch`, `agreement_negation_mismatch`. `cross_check_and_store` writes only `agreement` and its reasons.
- **Conflicts (JAR-47, `conflicts.py`).** Claims that cite different sources and share a subject, or a claim and another source's text, are compared for number, date and negation mismatches. A conflict is stored in `research_conflicts` as ids plus a fixed `kind` (no claim or page text), status `open`. Nothing resolves it automatically: only `ResearchRepository.resolve_conflict(id, resolution)` with a fixed code (`both_reported`, `first_preferred`, `second_preferred`, `not_a_conflict`) closes one, detecting again never reopens or duplicates it, and a final session refuses changes. The detail endpoint lists conflicts (ids, kind, status, resolution, timestamps) for the reader.
- **Additional-search decision (JAR-48, `search_decision.py`).** A pure function over a `SearchState` and the level's `LEVEL_BUDGETS` row returns `continue` or `stop` with one reason code. Budget stops (the level does not search, time, pages, queries) come first, then unexecuted planned queries, then the extra-round limit and "the last round found nothing new", then evidence gaps (no sources, too few relevant sources, open conflicts, no authoritative source, only stale sources), and otherwise `sufficient_coverage`. A stop with unmet gaps lists them as caveats, so a budget stop is never reported as completeness. Thresholds are proposals (`DecisionThresholds`, minimum relevant sources per level) and can be overridden.

Limits, stated plainly. The fact checks read surface forms (numbers with a known unit, dates, a negation word, capitalised names); they are heuristics, not understanding. They can flag a different year of the same statistic or an unrelated "not", and miss a paraphrase or an implicit contradiction. Agreement between sources can be one copying another. Agreement and conflict records say that the surface facts line up or differ, never that a claim is true; a person decides.

## Research screen

`GET /research` serves the Research screen: a form to request a research (see below) above a read-only browser of stored sessions. The browser is backed by two read-only endpoints in `backend/api/research.py`:

- `GET /api/research/sessions` lists sessions (`limit` 1 to 100, default 50; optional `status`). Rows are summaries: id, question, level, status, failure reason code, whether a result exists, and timestamps. Sessions come newest first (`created_at`, then `id`, both descending; `ResearchRepository.list_sessions(..., newest_first=True)`), and there is no paging, so a list that hits the limit covers only the newest sessions; the screen says so and asks the server for the chosen status instead.
- `GET /api/research/sessions/{id}` returns one session with its result text, queries, sources (title, URL, final URL, publisher, source type, the five ratings, dates) and claims. Each claim carries its stored quote, optional offsets, and the id of the source it cites. Since schema v8 each source also carries `classification` (`rule`, `basis`) and `reasons` (fixed codes per rating), and the session carries `conflicts` (ids and fixed codes only). The content digest is not exposed. While this server process is running the session, the detail also carries `progress` (see below); otherwise the key is absent and the body is unchanged.

Responses are built from explicit field allowlists. An unknown or malformed id is `404 session_not_found`; a bad `limit` or `status` is `422 invalid_limit` or `422 invalid_status`; a storage failure is `503 storage_unavailable`. Error bodies are fixed codes and never repeat the request or stored text. The GET routes never search, fetch pages, or call a model.

The screen is plain HTML and JavaScript (`frontend/research.html`, `research.js`, `research-api.js`, `research-view.js`, the request panel in `research-run.js`, `research-run-api.js`, `research-run-view.js`, and `research.css`). The list polls every 5 seconds (with backoff on errors), refreshes a running session's detail, and stops re-reading a session once it is finished. All stored text is rendered as text nodes. A source URL becomes a link only for `http` and `https`, with `rel="noopener noreferrer"` and `target="_blank"`; anything else is plain text. A banner states that the page is local, that a citation only means the quote was found verbatim in the stored source text (not that the claim is true), and that the 0 to 1 ratings are heuristic. To look at the browser with fake stored data, run `python scripts/dev_research_demo_server.py` (loopback only, port 18921 by default, a temporary SQLite file seeded through `ResearchRepository`, never your own database or `.env`) and open the printed URL. It includes sessions whose text contains HTML and script-like strings to show that they render inertly. Stop it with Ctrl-C or SIGTERM; the temporary database is removed.

## Requesting a research (off by default)

A research can be requested from the screen only when three things are all true: `JARVIS_RESEARCH_ENABLED=1`, a search provider is configured (`JARVIS_SEARCH_PROVIDER` is not `none`), and a chat provider is configured. With any of them missing the screen shows the form disabled with the reason, `GET /api/research/status` returns `{"enabled": false, "reason": "disabled" | "no_search_provider" | "no_chat_provider"}`, and both POST routes answer `503 {"detail": "research_not_configured"}`. An invalid `JARVIS_RESEARCH_ENABLED` value stops startup with a configuration error. How to turn it on, and exactly what is sent where, is in [research-search.md](research-search.md#using-it-from-the-research-screen).

**Routes** (`backend/api/research.py`; the pipeline itself is imported only when research is enabled, so the app starts without the HTTP client library otherwise):

| Route | Result |
| --- | --- |
| `GET /api/research/status` | `{"enabled": true}` or `{"enabled": false, "reason": ...}` |
| `POST /api/research/sessions` with `{"question": str, "level": "quick" \| "standard"}` | `202 {"id": ...}` |
| `POST /api/research/sessions/{id}/cancel` | `200 {"id": ..., "status": "cancelled" \| "cancelling"}` |

Every error is a fixed `detail` code and never echoes the request, a query, a URL or vendor text: `422` `question_required`, `question_too_long` (over 2000 characters), `question_invalid_characters` (control characters other than newline and tab), `invalid_level` (`deep`, `extensive` and `memory` are not available), `invalid_body` (not exactly `question` and `level`); `415 unsupported_media_type` (the body must be JSON); `413 invalid_body` (over 16 KiB); `429 busy` (one research may be queued or running at a time); `429 search_budget_exhausted` (the local monthly guard is used up; refused before anything is queued); `404 session_not_found`; `409 not_cancellable` (already finished); `403 forbidden`; `503 research_not_configured` or `storage_unavailable`. Other methods are `405`.

**Same-origin guard.** Both POSTs refuse a request whose `Origin` (else `Referer`) does not name the host it was addressed to, whose `Origin` is `null`, or whose `Sec-Fetch-Site` is not `same-origin`/`none`, with `403 forbidden`. This applies with login off too, so a web page on another site cannot make the visitor's browser start a search that spends credits. A request with none of those headers (curl, scripts) is not a browser fetch and is let through; with login on, the login layer is stricter and requires the header. The check is shared with the login layer (`backend/api/origin.py`).

**How it runs.** `backend/research/runner.py` (`ResearchRunService`) uses the existing task queue ([tasks.md](tasks.md)). A request creates the research session and queues one task whose goal is the fixed label `web research` plus the session id (never the question) and whose five steps are the stages. A single in-app worker, started in the application lifespan only when research is enabled, claims one task at a time and runs `QuickResearch` or `StandardResearch` with the injected parts: the budget-guarded search provider, a real `PageReader` over `HttpxTransport`, and the application's chat provider. Stage progress moves the task's steps forward; Standard reports its own stages and Quick's are observed through its search, reader and model calls. Cancelling a queued task cancels it at once; cancelling a running one sets the queue's token (Standard stops at its next checkpoint, Quick is cancelled), and the session ends `cancelled` with no result.

A task is **verified** only when its session ended `completed` and either has at least one stored verified claim (its quote was found word for word in the cited page) or carries the explicit notice that no claim could be verified. `completed` therefore never means that an answer was made up; a run whose model output has no verifiable quote ends `failed(synthesis_failed)` instead.

**Restart and shutdown.** At startup `recover()` marks tasks left running as `failed(interrupted)` and fails their unfinished research sessions (`internal_error`; the stored failure codes have no "interrupted"); nothing is re-run, because a research may already have spent a search credit. A queued request survives a restart and runs. On shutdown the worker is cancelled: the current run is stopped (its session ends `cancelled`, its task `failed(interrupted)`) and no task is left behind. The queue's own 900 s timeout is only a backstop; the research budgets (120 s quick, 300 s standard) end a run first as `failed(timeout)`.

**Progress.** While the server runs a session, `GET /api/research/sessions/{id}` adds `"progress": {"stage": planning|searching|reading|verifying|writing, "round", "queries", "pages", "sources", "claims"}` (numbers and a stage code only). The screen polls this every 2 seconds (backing off to 15 s on errors, paused while the tab is hidden) and also picks up a run that is still going after a page reload. Results show the verified claims with their quotes and a link to each source, the open conflicts and the caveats in separate boxes, and a line that citations are verified verbatim quotes while ratings are heuristic. A failure shows the fixed reason in Japanese.

Not available: deep and extensive research, retry, deleting a research, memory notes as search input (queries are built from the question only), and more than one research at a time. To try the screen without any service, run `python scripts/dev_research_run_demo_server.py` (loopback, port 18971, a temporary database, fake search, pages and model only; markers such as `#fail`, `#slow`, `#hostile`, `#conflict` and `#nothing` in the question pick the scenario; `--research-off` shows the unavailable state). It never reads `.env` or a key.

## Research from chat (off by default)

With a conversation router ([router.md](router.md)) and research fully configured (`JARVIS_ROUTER=rule|llm`, `JARVIS_RESEARCH_ENABLED=1`, a search provider and a chat provider), a chat turn the router really decides is `research` starts a research the same way the form does: `ChatService` calls `ResearchRunService.submit` through a small port (`backend/chat/research_start.py`, `RunServiceStarter`), so the one-at-a-time rule, the local search budget, the worker, the task queue and the Research screen are all the existing ones. There is no other execution path.

- **Level.** `JARVIS_CHAT_RESEARCH_LEVEL` is `quick` (default; the cheaper one) or `standard`. Nothing else is accepted.
- **Question and privacy consequence.** The research question is the user's whole message, unchanged, and nothing else: no memory note, no history, no earlier turn. That whole message is therefore sent to the search service (Tavily) as a query source and its text is subject to that service's retention, exactly as for a question typed into the form, and it is also sent to the router first (to the chat model with `JARVIS_ROUTER=llm`). The router cannot tell a question from a message that merely contains private text, so only enable this where that is acceptable. The fixed reply states that the message text is sent to the search service. A message the run service would refuse (blank, over 2000 characters, control characters) is not started; the Main Agent answers.
- **Reply.** A fixed Japanese message, no model call, with the link `/research#<session id>`. The Research screen selects a session from the URL hash, so the link opens that research and follows it while it runs. The chat itself does not follow the run, and a failed or cancelled research is shown only on the Research screen.
- **Not started.** A router fallback or a low-confidence decision never starts a research. When the run service answers busy, budget exhausted, not available or refused, the Main Agent answers as before and the Activity View says why (`research_skip`, see [chat.md](chat.md#research-from-chat)).
- **Cost.** Each started research spends search credits like one started from the form (Quick plans a bounded number of queries). Routing can misjudge, so a message that did not need research can still spend them; the budget cap and the single-run rule are the guards.
- **Tested with fakes only.** No live search, router or model has been exercised for this path.
- **Trying it without any service.** `python scripts/dev_research_run_demo_server.py --chat` serves the chat page as well, with a fake router (markers such as `#research`, `#casual`, `#lowconf` in the message), a fake chat model and the same fake search and pages. Loopback only, temporary database.
